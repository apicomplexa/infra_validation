# infra_validation

Проверка объектов городской инфраструктуры (Архангельск, Северодвинск,
Новодвинск) из выгрузок подрядчика по независимым источникам. В копию каждой
выгрузки дописываются три колонки:

- **«Подтверждено»**: 1, если о существовании объекта говорят не меньше двух
  независимых источников;
- **«Вид?»** («Общепит?», «Алкоголь?», «Табак?»): того ли объект вида, что в
  выгрузке;
- **«Основания»**: где найден объект и что искали, но не нашли.

Источники: OSM и 2GIS (флаги выгрузки), Яндекс Карты, реестр администрации,
Overture Places, Foursquare OS Places, реестр лицензий ФСРАР (ЕГАИС).

Код перенесён из архивного репозитория `infrastructure_2026` (тег
`archive-2026-10-30`) один к одному. Паритет со старыми выходами проверяется
тестами. Устройство описано в [`docs/ARCHITECTURE.md`](docs/ARCHITECTURE.md),
схема потока — в [`docs/architecture.qmd`](docs/architecture.qmd).
Как пользоваться, DAG по категориям, dataflow каждой метрики и алгоритмы
матчеров со схемами — в [`docs/workflow.qmd`](docs/workflow.qmd)
(`pixi run docs` → `results/docs/architecture.html`, `results/docs/workflow.html`).

## Быстрый старт

Нужен [pixi](https://pixi.sh) и Linux x86-64.

```bash
pixi install          # окружение: Python 3.14, Snakemake, pandas, duckdb, Quarto
pixi run dry-run      # что будет выполнено
pixi run workflow     # весь конвейер, офлайн (~1–2 мин с нуля, включая разбор реестра)
pixi run test         # юнит-тесты и регрессия против resources/golden/
```

Сеть нужна только явно вызываемым командам:

| Команда | Что делает |
|---|---|
| `pixi run yandex-fetch` | дочитывает в кэш страницы Яндекса для объектов, чей вердикт от них ещё зависит |
| `python -m infracheck.fetch.overture --help` | снимок Overture Places для трёх городов |
| `python -m infracheck.fetch.foursquare --help` | снимок FSQ OS Places (нужен токен Hugging Face, сохранённый `hf auth login`) |

После `yandex-fetch` повторный `pixi run workflow` пересчитывает только
зависящие от кэша шаги.

## Поставка `finalest`

Все девять XLSX из `data/raw/finalest/` (три города × три категории)
перечислены в `config/deliveries_finalest.tsv`. Конфиг `config/finalest.yaml`
дополняет основной; результаты записываются в `results/finalest/`, логи —
в `logs/finalest/`. Прежние поставки и результаты сохраняются.

```bash
pixi run finalest-dry-run       # проверить план
pixi run finalest               # весь расчёт с существующим кэшем, без сети
pixi run finalest-yandex-fetch  # дочитать недостающие запросы Яндекса
pixi run finalest               # пересчитать с дополненным кэшем
```

Для ночного запуска все три этапа объединены в одну команду. На удалённой
машине сначала нужны актуальный код, `pixi install`, девять исходных XLSX
и файлы из `resources/`, включая оба кэша Яндекса. Данные и кэши не входят
в git, их нужно перенести отдельно.

```bash
mkdir -p logs/finalest
nohup pixi run finalest-night > logs/finalest/night.log 2>&1 &
```

Ход запросов записывается в `logs/finalest/yandex_fetch.log`. Успешные ответы
сохраняются после каждого запроса; повторный запуск продолжит недостающие.
Несколько строк с одинаковым поисковым URL требуют одного запроса. Ошибки
сети не кэшируются; их можно повторить тем же запуском.

В XLSX алкоголя и табака каждая исходная строка остаётся отдельной записью:
одна вывеска может одновременно иметь тип магазина и общепита. `trade`,
Direct/Inferred и обучение брендов определяются теми же правилами, что
для CSV v4. Табак и алкоголь сопоставляются с ЕГАИС вместе в пределах
каждого города; существующее объединение записей используется в сводках.
Группировка общепита, пороги и правила подтверждения сохраняются.

## Что где лежит

| Путь | Содержимое |
|---|---|
| `config/deliveries.tsv` | что проверять: строка = поставка (город × категория × файл) |
| `config/config.yaml` | все пороги, правила независимости, словари вида, тексты — по категориям ([`config/README.md`](config/README.md)) |
| `src/infracheck/` | библиотека: `core/` контракты, `inputs/` адаптеры входа, `checks/` проверки, `categories/` правило категории, `deliver/` запись XLSX |
| `packages/licmatch/` | отдельный пакет сопоставления с реестрами: `licmatch.match()` |
| `workflow/` | Snakemake: правила вызывают тонкие скрипты, логика — в `src/` |
| `data/raw/` | поставки подрядчика (не в git, только чтение) |
| `resources/` | реестр ФСРАР, снимки Overture/FSQ, кэш Яндекса, эталоны регрессии (не в git) |
| `results/` | выходы: `<поставка>/…_подтверждено.xlsx`, `<категория>_summary.txt` |
| `docs/changes/` | изменения, сдвигающие результаты, с таблицами «что изменилось» |

## Новая поставка или категория

- **Поставка в уже известном формате** — новая строка в `config/deliveries.tsv`.
- **Новый формат файла** — адаптер в `src/infracheck/inputs/` и значение
  `format` в схеме.
- **Новая категория** — блок `categories.<имя>` в `config/config.yaml`
  (проверки, их пороги, независимость, словари вида, тексты легенды) и модуль
  `src/infracheck/categories/<имя>.py`, который этот блок называет.

## Чего нельзя утверждать

«Подтверждено = 1» не означает, что объект работает сегодня и что он
относится к своему типу. «Подтверждено = 0» не означает, что объекта нет:
это очередь для ручной проверки. Находка в Яндексе — не лицензия. Табачный
слой не подтверждается реестром: в реестре нет табака.

## Калибровка и независимая оценка

После завершения запросов Яндекса и пересчёта finalest проверьте настройки
`config/calibration.yaml` и выполните команды из корня проекта:

```bash
export PYTHONPATH=src:packages/licmatch/src
pixi run calibration-sample
pixi run calibration-audit --sample A
pixi run calibration-audit --sample B
pixi run calibration-audit --sample A --escalate
pixi run calibration-audit --sample B --escalate
pixi run calibration-evaluate
pixi run calibration-human-check
```

Аудит обращается к Codex и сети; `--dry-run` показывает объём работы,
`--limit N` ограничивает число объектов в запуске. Повторный запуск
продолжает работу по кэшу `resources/cache/audit/`. После заполнения
`results/finalest/calibration/human_check_B.xlsx` повторно запустите
`calibration-evaluate`, чтобы учесть ответы человека. Выборки, таблицы и
отчёт находятся в `results/finalest/calibration/`; запечатанные выборки
содержат вердикты конвейера и не предназначены для аудитора или проверяющего.
`manifest.json` защищает от повторной выборки: её изменение требует явно
удалить манифест и зафиксировать причину в `docs/changes/`. Порядок работы,
условия применения и ограничения оценки приведены в
[протоколе калибровки](docs/calibration_protocol.md).
