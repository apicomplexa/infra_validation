# Протокол калибровки и оценки точности: аудитор-агент

Статус: проект протокола, 2026-11-21. Утверждается **до** того, как будет
посмотрена хоть одна метка выборки B. Всё, что ниже названо «предрегистрацией»,
фиксируется коммитом с тегом `calibration-protocol-v1` до запуска сэмплера.

Цель — ответить на два разных вопроса и не смешивать их:

1. **Существует ли объект** (сейчас, по этому адресу) — проверка флага
   «Подтверждено».
2. **Того ли он вида** (общепит / продаёт алкоголь / продаёт табак) —
   проверка оси «Общепит?/Алкоголь?/Табак?».

Эталон — вердикт аудитора-агента, сам проверенный выборочной ручной разметкой
(§5). Оценка распространяется на 9 поставок `data/raw/finalest` и ни на что
другое: перенос на другие города, классы или даты — экстраполяция.

## 1. Выборка

### 1.1. Единица

Единица выборки — **склеенный объект**: пара (`delivery`, `merged`) из
`results/finalest/<category>_objects.csv`. Не строка выгрузки (вывеска
повторяется под каждым типом) и не запись `object_id` (подрядчик пишет одну
вывеску дважды, OSM и 2GIS рядом; в алкоголе и табаке `merged` ещё и
объединяет записи одного магазина в лицензионном join). Сейчас: 4 095
склеенных объектов (5 366 записей с собственным `object_id`).

Вердикт склеенного объекта:

- существование: `conf` или `not` по `confirmed_object` — вердикту правила
  категории по объединённым свидетельствам всех записей объекта; флаг
  `mixed` выставляется отдельно, если этот вердикт отличается от `confirmed`
  хотя бы одной записи;
- вид: значение оси, если оно одно у всех записей, иначе `mixed`.

Аудитор проверяет объект по **представительной записи** — с наименьшим
`object_id` (это и есть номер `merged`).

### 1.2. Страты

Страт = поставка × вердикт конвейера (36 ячеек, часть пустые):

| Страт | Условие |
|---|---|
| S1 | подтверждён, вид = «да» |
| S2 | подтверждён, вид ∈ {«нет», «автомат», «противоречие»} |
| S3 | подтверждён, вид ∈ {«нет данных», `mixed`} |
| S4 | не подтверждён по `confirmed_object` (любой вид) |

Страты строятся по результатам **после** завершения текущего Яндекс-прогона и
перезапуска `pixi run workflow`; до этого сэмплер не запускается. Таблица в
§1.4 посчитана по результатам до прогона и только задаёт масштаб: в алкоголе и
табаке Яндекс сейчас опрошен у ~2–5 % объектов, так что S3 и S4 там заметно
перераспределятся.

### 1.3. Размеры и распределение

Параметры конвейера заданы **на категорию, а не на город**, поэтому
калибровке (A) нужна точность по категории, а не по файлу; итоговой оценке (B)
— по файлу.

| Город | A на файл | B на файл | Комментарий |
|---|---|---|---|
| Архангельск | 50 | 60 | |
| Северодвинск | 45 | 50 | |
| Новодвинск | 20 | 35 | N = 75 / 107 / 78; доля выборки B f = 0,47 / 0,33 / 0,45, поправка на конечность обязательна |

Итого A = 345, B = 435, вместе 780 проверок аудитором.

- **B**: внутри файла n_h ∝ √N_h (компромисс между пропорциональным
  распределением, лучшим для общей доли, и равным, нужным для малых стратов,
  на которых держится полнота), минимум min(N_h, 5) на страт; страт с
  N_h ≤ 5 берётся **сплошь** (вес 1, нулевая выборочная дисперсия).
- **A**: равное распределение по стратам из того, что осталось после B,
  ограниченное N_h − n_B,h. Цель A — найти ошибки, а не оценить долю, поэтому
  A сознательно перевзвешивает S2–S4.
- Ожидаемая точность B (95 %, p ≈ 0,8): по категории ±7–8 п. п., по файлу
  Архангельска или Северодвинска ±11–13 п. п., по файлу Новодвинска ±9–11 п. п.
  (с поправкой на конечность). Оценка доли **внутри одного страта** файла —
  ±20 п. п. и шире; по стратам выводов не делать.
- **Дозабор.** Если полуширина 95 % ДИ полноты по категории в B больше
  15 п. п., B добирается следующими по порядку объектами того же страта
  (§7) — по заранее заданному критерию ширины интервала, никогда по значению
  точечной оценки.

### 1.5. Зерно и непересекаемость

Порядок объектов внутри страта задаётся не генератором, а хешем:
`rank = sha256("{seed}|{delivery}|{merged}")`. Первые n_B,h объектов страта по
`rank` идут в B, следующие n_A,h — в A, следующие — резерв дозабора. A и B не
пересекаются по построению, каждое по отдельности — простая случайная выборка
без возвращения из страта. Порядок не зависит от порядка строк в CSV и не
меняется при перестройке стратов. `seed` хранится в `config/calibration.yaml`
(`seed`), фиксируется до запуска и не меняется никогда:
перевыборка «с другим зерном» запрещена.

Записи, вручную проверенные руководителем, остаются в фрейме (иначе оценка
перестаёт описывать всю поставку). Их метки используются в калибровке как
примеры ошибок (это уже калибровочная информация), а в B учитываются, только
если объект попал в B случайно.

### 1.6. Перевзвешивание к популяции

Вес объекта в B: w_i = N_h / n_h. Любая метрика — отношение двух сумм
Хорвица — Томпсона, θ = Σ w_i a_i / Σ w_i b_i (точность: a = «объект реален
∧ подтверждён», b = «подтверждён»; полнота: a = «реален ∧ подтверждён»,
b = «реален»; доля реальных объектов: b ≡ 1). Это верно и после калибровки,
когда вердикты конвейера меняются и перестают совпадать со стратами: веса
определяются **схемой выборки**, а не текущим вердиктом.

Дисперсия — линеаризацией: z_i = (a_i − θ b_i) / B̂, Var(θ) = Σ_h N_h²
(1 − f_h) s²_{z,h} / n_h, f_h = n_h / N_h. Интервал — Уилсона с эффективным
объёмом n_eff = θ(1 − θ) / Var(θ) (Korn — Graubard); при нулевой дисперсии во
всех стратах (все 0 или все 1) — Уилсон по невзвешенному n. Контроль —
стратифицированный бутстреп (4 000 повторов, ресэмплинг внутри страта,
масштабирование Рао — Ву с учётом f_h); при расхождении границ больше чем на
2 п. п. публикуется более широкий интервал.

## 2. Эталонные метки

Аудитор возвращает по объекту: `exists` (yes/no/unclear), `open`
(open/closed/unclear), `category_ok` (yes/no/unclear), для общепита ещё
`is_vending` (yes/no/unclear), цитату, URL с типом источника, дату
свидетельства, дату проверки.

Из них строятся две эталонные метки:

- **E — существует сейчас.** E = 1, если `exists = yes` и `open ≠ closed`;
  `exists = yes` требует свидетельства, датированного 2025-01-01 или позже,
  либо живой карточки справочника без отметки о закрытии на дату проверки.
  E = 0, если `exists = no` или `open = closed` (закрытые учитываются
  отдельно, как ошибка «подтверждён устаревший объект»). E = ?, если
  `exists = unclear`.
- **K — того ли вида.** Определена, если объект опознан (`exists = yes`, в
  том числе закрытый). K = `category_ok`. Для `exists = no` K не определена:
  метрики вида считаются на опознанных объектах. Критерий вида задаётся в
  инструкции аудитору: общепит — место, где готовят или подают еду и напитки
  (вендинг отмечается `is_vending`, а не `category_ok`); алкоголь/табак —
  явное свидетельство продажи (рубрика, ассортимент, фото, отзыв); тип
  объекта, совместимый с продажей («продуктовый магазин»), — это `unclear`, а
  не `yes`.

### 2.1. Уточнение «живой карточки» и проверки ссылок (2026-11-21)

Принято 2026-11-21 **до вскрытия выборки B**, по разведочной диагностике на A
(`results/finalest/calibration/diagnostics/recall_A.md`). Применяется
одинаково к A и B, вслепую по отношению к вердиктам конвейера, детерминированно
и только по кэшу страниц аудитора (`resources/cache/audit/urls/`), без новых
запросов к сети. Реализация — `src/infracheck/audit/verify.py`.

**Проверка ссылки (§5) проверяет место, а не только имя.** Ссылка получает
исход `verified`, только если страница называет объект (имя или цитата) **и**
помещает его туда же: в тексте, где страница говорит об объекте (заголовок и
описание карточки, иначе ближайшее окружение упоминания), стоит город объекта в
любой падежной форме (Архангельск, в Архангельске, Архангельская обл.;
Северодвинск; Новодвинск), а если там указан адрес — улица и дом совпадают с
адресом объекта (сравнение адресов — тем же разбором топонимов, что в
`licmatch`). Страница с именем, но другим городом или адресом, — `contradicted`.
Страница с именем, но без города и адреса, — `weak`: это не подтверждение.

**Сила метки.** `exists = yes` остаётся `yes`, только если среди
`verified`-ссылок есть хотя бы одно из:

- (а) **датированное свидетельство**: дата свидетельства аудитора с точностью не
  грубее месяца, не раньше 2025-01-01, не совпадает с днём проверки (дата
  проверки — не дата свидетельства) и стоит на самой проверенной странице;
- (б) **живая карточка первичного справочника**: карточка организации в
  Яндекс Картах (`/maps/org/`), 2ГИС (`/firm/`), страница во ВКонтакте или
  Одноклассниках, официальный сайт организации (домен читается как вывеска) —
  без отметки «Больше не работает» / «закрыто» там, где страница называет объект.

Агрегаторы-зеркала (zoon, spravker, orgpage, list-org, rusprofile, yell, flamp,
urbanplaces, mestam, openalfa и подобные) сами по себе не достаточны: многие из
них копируют 2ГИС или OSM, то есть ту же запись, из которой пришла выгрузка.
Страница пользователя, поиска или дома в Яндексе — не карточка организации.

Иначе `exists` становится `unclear`. Так же `open = open` требует (а) или (б),
иначе `unclear`. Исходные значения сохраняются в столбцах `exists_raw` и
`open_raw`, сила — в `label_strength` (`dated` / `live_card` / `weak`), причина
понижения — в `notes`. Метки `exists = no` и `open = closed` правило не трогает.

Инструкция аудитору (`config/audit_prompt.md`, `prompt_version: 3`) требует того
же явно. Ответы версии 2 в кэше сохраняются; при эскалации заново спрашиваются
только объекты, неясные после этого правила.

**«Неясно» не выбрасывается молча.** Для каждой метрики публикуются три
числа:

- θ_res — по разрешённым меткам (неясные исключены, веса перенормированы
  внутри страта; предполагается, что неясность случайна внутри страта) — с ДИ;
- θ_low — все неясные засчитаны **против** конвейера;
- θ_high — все неясные засчитаны **в пользу** конвейера.

[θ_low; θ_high] — интервал неидентифицированности (границы Мански). Если доля
неясных в категории > 20 %, заголовочным результатом служит этот интервал, а
не θ_res. Перед анализом неясные один раз проходят эскалацию (тот же аудитор,
расширенный список источников); результат эскалации хранится в отдельном
столбце, исходный вердикт сохраняется. Ожидаемо, что для табака `category_ok`
останется неясным у большинства; тогда результат по виду табака —
**«данных недостаточно»**, и это полный результат.

## 3. Метрики

**Существование** (флаг «Подтверждено» против E), по категории:

- доля реальных объектов в поставке P(E = 1) — качество **поставки**;
- точность (PPV) = P(E = 1 | подтверждён), NPV = P(E = 0 | не подтверждён),
  полнота = P(подтверждён | E = 1), специфичность = P(не подтверждён | E = 0) —
  качество **конвейера**;
- отдельно: доля закрытых среди подтверждённых.

Таблица сопряжённости 2 × 3 (подтверждён / нет × E = 1 / 0 / ?) приводится в
взвешенных оценках численности и рядом — в сырых счётах выборки. Поскольку
`n_sources` хранится, кривая «порог min_sources = 1, 2, 3 → точность,
полнота» считается на B без перезапуска и без подбора.

**Вид** (ось против K), по категории: таблица 6 × 3 (да / нет / автомат /
противоречие / нет данных / mixed × K = 1 / 0 / ?). Из неё:

- покрытие = P(вид ∈ {да, нет});
- точность «да» = P(K = 1 | да), точность «нет» = P(K = 0 | нет);
- доля объектов не своего вида в поставке P(K = 0);
- для общепита: доля «автомат», подтверждённых `is_vending = yes`.

«Нет данных» — отказ от решения, а не «да»: никогда не объединять.
«Противоречие» описывается распределением K, без точности.

**Объект верен целиком**: P(E = 1 ∧ K = 1) — одна цифра для поставки.

**По городам** — только где в знаменателе ≥ 20 разрешённых объектов B;
иначе сырые счёты без процентов. Новодвинск — всегда с поправкой на
конечность и с пометкой о малом N.

**Множественные сравнения.** Первичные конечные точки (12): по каждой из трёх
категорий — P(E = 1), PPV и полнота «Подтверждено», точность «да» по виду.
Для них приводятся 95 % ДИ и, рядом, ДИ с поправкой Бонферрони (99,6 %). Всё
остальное (города, страты, матрицы, кривая порогов) — разведочный анализ, и
так и подписывается.

## 4. Калибровка (только на A)

**Настраиваемое** — числовые пороги из `config.yaml`, пересчитываемые офлайн из
кэшей (без новых запросов к сети на каждую конфигурацию). Не более трёх
параметров на категорию, грубая сетка:

| Параметр | Сейчас | Сетка |
|---|---|---|
| `policy.yandex.name_min` (и `providers.name_min`) | 72 | 65, 72, 80 |
| `policy.overture.name_min` = `foursquare.name_min` | 85 | 80, 85, 90 |
| `policy.foursquare.fresh` | 2022-01-01 | 2020, 2022, 2024 |
| `near_m` / `generic_m` (общие для Яндекса, Overture, FSQ) | 150 / 60 | 100/40, 150/60 |

**Не настраивается:** `existence.min_sources` (это определение утверждения;
вместо подбора — кривая порогов из §3); параметры `licmatch` (у них своя
методология калибровки, `packages/licmatch/docs/METHODOLOGY.md`, — только как
анализ чувствительности); группы независимости; `relink_m` /
`relink_generic_m` (влияют на единицу выборки — менять их значит менять фрейм).

**Правила-лестницы** (регулярные выражения вида, список «общих» вывесок) —
не параметры сетки. Изменение допускается только как исправление дефекта:
≥ 3 случая одного механизма в A, юнит-тест, запись в `docs/changes/`. Каждое
такое исправление считается степенью свободы калибровки и перечисляется в
отчёте.

**Процедура.**

1. Целевая функция на A — взвешенная (веса A: N_h / n_A,h) сбалансированная
   точность существования (среднее полноты и специфичности); для оси вида —
   точность «да» при покрытии не ниже текущего.
2. Публикуются результаты **всех** конфигураций сетки, не только лучшей.
3. Выбор — правило одной стандартной ошибки: из конфигураций, отстающих от
   лучшей не более чем на 1 SE, берётся ближайшая к текущей. Текущая
   конфигурация побеждает при ничьей.
4. Устойчивость: изменение принимается, только если выигрыш имеет тот же
   знак при исключении каждого из трёх городов по очереди.
5. **Правило остановки:** не более двух раундов; остановка раньше, если выигрыш
   лучшей конфигурации < 1 SE или < 3 п. п. Затем конфигурация замораживается
   (тег `calibration-frozen`), конвейер перезапускается **один раз**, и B
   оценивается для текущей и для выбранной конфигурации на одних и тех же
   объектах: парная разность с ДИ по бутстрепу. Если ДИ разности содержит 0 или
   разность отрицательна — откат к исходной конфигурации; результат B
   публикуется как есть.
6. B больше не используется для настройки. Если после B всё-таки нужна правка,
   B становится калибровочной, а для оценки нужна свежая выборка C из резерва
   (в Новодвинске резерва не хватит — тогда так и пишется, что независимой
   оценки по Новодвинску после второй правки нет).

## 5. Проверка аудитора человеком

- **Объём и отбор.** 30 объектов из B после того, как аудитор закончил B
  целиком; стратификация по **вердикту аудитора**: ~12 с E = 1, ~12 с E = 0
  (из них ≥ 4 закрытых), ~6 неясных; ≥ 8 объектов на категорию; ≥ 8 — где
  аудитор расходится с конвейером. Порядок внутри — по тому же хешу.
- **Слепота.** Человек видит ровно то же, что аудитор (название, адрес, город,
  заявленный вид, координаты), не видит ни вердикта аудитора, ни вердикта
  конвейера; заполняет ту же схему меток; может пользоваться любым источником,
  включая звонок или визит.
- **Метрики.** Сырое согласие и каппа Коэна по каждой оси (`exists`, `open`,
  `category_ok`, и производной E) с бутстреп-ДИ; матрица ошибок аудитора
  P(человек | аудитор), взвешенная к распределению вердиктов аудитора в B
  (отбор стратифицирован по нему, поэтому оценка внутри страта несмещённая).
  При 30 объектах ДИ каппы порядка ±0,15–0,20 и согласия 90 % — примерно
  [0,74; 0,97]: 30 проверок обнаруживают плохого аудитора, но не доказывают
  отличного.
- **Решение.** κ ≥ 0,8 и согласие ≥ 90 % — аудитор принимается как эталон.
  0,6 ≤ κ < 0,8 — принимается с поправкой на ошибку классификации (оценки B
  пересчитываются через матрицу ошибок; публикуются и исправленные, и
  неисправленные). κ < 0,6 или систематическая ошибка (например, «существует»
  по несуществующему URL) — аудитор эталоном не является: правится инструкция,
  B переразмечается, и проверяются **новые** 30 объектов (старые
  использованы для диагностики).
- **Проверка ссылок** — до человеческой: каждый URL автоматически открывается,
  цитата ищется на странице. Недоступная ссылка или ненайденная цитата
  понижает вердикт до `unclear`; доля таких случаев (галлюцинаций)
  публикуется. С 2026-11-21 ссылка подтверждает объект, только если на
  странице совпадают и имя, и место (город, а при наличии адреса — улица и
  дом), а `exists = yes` / `open = open` требуют датированного свидетельства
  или живой карточки первичного справочника — см. §2.1.

## 6. Независимость

Аудитор вправе пользоваться Яндексом и 2ГИС, но конвейер сам опирается на них
(Яндекс — источник, OSM/2ГИС — происхождение самой выгрузки). Поэтому:

- у каждого URL записывается тип источника: `yandex`, `2gis`, `osm`, `vk`,
  `official`, `registry` (ЕГАИС, ФНС, rusprofile), `review`, `other`;
- для объекта вычисляется, опирается ли вердикт аудитора **только** на
  источники, которые конвейер для этого объекта уже засчитал (столбцы
  `src_*`) — «зависимый вердикт»;
- анализ чувствительности: все метрики пересчитываются с зависимыми
  вердиктами, переведёнными в `unclear` (с границами из §2), и отдельно — без
  вердиктов, опирающихся только на Яндекс. Если основной и
  чувствительный результаты расходятся больше чем на ширину ДИ, заголовком
  служит чувствительный, а основной идёт с оговоркой о циркулярности;
- лицензионный реестр ФСРАР для алкоголя — тот же источник, что `egais` в
  конвейере; вердикт `category_ok = yes`, опирающийся только на него, —
  зависимый.

Даты: снимки источников конвейера — октябрь–ноябрь 2026, проверка аудитора —
позже; закрытия в промежутке смещают оценку против конвейера. Дата проверки
хранится у каждой метки.

## 7. Спецификация сэмплера (без реализации)

`workflow/scripts/calibration_sample.py`, вызывается отдельной задачей pixi
(`pixi run calibration-sample`), не входит в `all`.

**Входы:** `results/finalest/{catering,alcohol,tobacco}_objects.csv`;
`config/deliveries_finalest.tsv`; `config/calibration.yaml` (`seed`,
`n_A`, `n_B` по городам, `min_per_stratum = 5`, `topup_reserve = true`,
`exclude_ids` — пусто по умолчанию); файл ручных проверок руководителя (только
для пометки `supervisor_checked`).

**Выходы** в `results/finalest/calibration/`:

- `frame.csv` — все склеенные объекты: `unit_id` (`delivery:merged`),
  `delivery`, `category`, `city`, `merged`, `object_ids` (через `;`),
  `n_records`, `stratum`, `ver_exists` (conf/not/mixed), `ver_kind`,
  `n_sources_max`, `sources`, `ya_status`, `rank` (hex), `rank_in_stratum`,
  `sample` (B / A / reserve), `supervisor_checked`;
- `allocation.tsv` — `delivery`, `stratum`, `N_h`, `n_B_h`, `n_A_h`,
  `w_B = N_h / n_B_h`, `w_A`, `f_B`, `census` (bool);
- `sample_A.csv`, `sample_B.csv` — строки `frame.csv` выборки с весом;
  **запечатаны**: вердикты конвейера в них есть, аудитору и человеку они не
  передаются;
- `auditor_input_A.csv`, `auditor_input_B.csv` — только `unit_id`, `name`,
  `address`, `city`, `claimed_category` (категория + `types`), `lat`, `lon`,
  в порядке `unit_id` (не по страту, чтобы порядок не подсказывал вердикт);
- `manifest.json` — `seed`, sha256 каждого входа, коммит git, хеш блока
  `categories` в `config.yaml`, дата, версия сэмплера.

**Схема ответа аудитора** (`auditor_labels_{A,B}.csv`): `unit_id`, `exists`,
`open`, `category_ok`, `is_vending`, `quote`, `urls`, `url_types`,
`evidence_date`, `audit_date`, `auditor_model`, `escalated`, `notes`.

**Инварианты (тесты):** повторный запуск даёт побайтно одинаковые файлы;
A ∩ B = ∅; Σ n_h по файлу равна заданному n; каждый `merged` встречается во
фрейме один раз на поставку; `auditor_input_*` не содержит ни одного столбца
вердикта или источника; сэмплер отказывается работать, если в результатах
есть объекты с `needs_yandex = True` и пустым `ya_status` (Яндекс-прогон не
завершён) или если `manifest.json` уже существует (перевыборка — только
явным удалением и записью в `docs/changes/`).
