# Методология сопоставления объектов с реестром лицензий

`licmatch` — правило связывания записей (record linkage) между выгрузкой
объектов городской среды и государственным реестром лицензий. Документ
описывает, что именно делает правило, почему оно устроено так, чем проверено и
какие утверждения на его результате **недопустимы**.

Реализация: `packages/licmatch/src/licmatch/`. Прикладной слой для настоящего
исследования (адаптеры к четвёртой поставке и к выгрузке ЕГАИС, колонки
`licence_*`, интерпретация «чего это свидетельство») — `src/arkhinfra/v4_egais.py`,
запуск — `pixi run match-egais-v4`, прикладное описание результата —
`docs/v4_egais_match.md`.

## 1. Задача

Дано два независимых описания одних и тех же торговых точек:

- **выгрузка объектов** — название («вывеска»), адрес одной строкой, координата;
- **реестр лицензий** — наименование **лицензиата** (юридического лица), адрес
  места осуществления деятельности в отдельных полях, координата (часто
  отсутствующая или грубо округлённая), статус и срок действия лицензии.

Требуется для каждого объекта ответить: **есть ли по этому адресу лицензия,
действует ли она, и какая именно**. Ответ нужен пообъектный и защитимый
построчно: результат идёт в отчёт, где каждую строку можно оспорить.

Это отличает задачу от агрегатной оценки близости (доля объектов рядом с
лицензированной точкой), которую в этом проекте отдельно считает
`v4_common.corroboration()`. Агрегат терпим к ошибкам, которые взаимно
компенсируются; пообъектный ответ — нет.

Три свойства, которые правило обязано иметь:

1. **Консервативность на соседях.** Ошибка «приписали лицензию соседнего дома»
   дороже, чем пропуск: она превращается в ложное утверждение о конкретном
   объекте.
2. **Прозрачность.** Каждая принятая пара должна разбираться на слагаемые,
   которые можно прочитать и оспорить по отдельности.
3. **Отсутствие скрытой фильтрации.** Ни один кандидат не должен отсеиваться до
   того, как его увидела функция оценки: иначе доля пропусков перестаёт быть
   измеримой.

## 2. Почему не подходят стандартные решения

**Расстояние редактирования по адресным строкам.** Источники пишут одну и ту же
дверь в несовместимом порядке, с разными сокращениями и в разных падежах:

| выгрузка объектов | реестр |
| --- | --- |
| `Архангельск, набережная Северной Двины, 55` | `Северной Двины Набережная, 55` |
| `Архангельск, улица Тимме, 2 к5` | `Тимме Я. Улица, 2, 5` |
| `Архангельск, Ленинградский проспект, 356 к4` | `Ленинградский пр-кт, 356, 4` |
| `Лесная речка, Лахтинское шоссе, 17` | `Лахтинское ш, 17` + `Лесная речка` |

Посимвольная метрика на таких парах — шум: она одновременно штрафует за
перестановку слов (различие безразличное) и почти не штрафует за смену номера
дома (различие решающее).

**Только координаты.** Координаты реестра получены пересчётом из
градусов-минут-секунд: одна угловая секунда округления — уже ≈ 31 м широты
(тест `test_geo.py::test_one_arcsecond_of_latitude`). Внутри радиуса в 100 м
соседнее здание неотличимо от искомого. Кроме того, у 47 % строк реестра
пригодной координаты нет вовсе.

**Сопоставление по названию.** Реестр называет **лицензиата**, выгрузка —
**вывеску**. Крупнейшие держатели лицензий в городе — `АО "Тандер"`,
`ООО "Агроторг"`, `ООО "Альбион-2002"`, `ООО "Альфа-М"`; на улице это Магнит,
Пятёрочка, Бристоль и Красное&Белое. Никакая нечёткая метрика этот разрыв не
покрывает.

**Внешнее геокодирование.** Отправлять адреса во внешний сервис — значит
заменить контролируемую ошибку неконтролируемой (чужая версия адресного
классификатора, недоступная для аудита) и сделать результат невоспроизводимым
без сети.

Отсюда конструкция: **адрес разбирается в топонимы и сравнивается по полям**,
название работает тай-брейкером, расстояние — третьим, слабейшим доводом.

## 3. Модель данных: две канонические стороны

Пакет не знает ни одного источника. Адаптер (в этом проекте —
`arkhinfra.v4_egais`) приводит свою сторону к канонической схеме, и дальше ни
одна функция не может определить, откуда сторона пришла:

```python
side(toponyms, names, latitude, longitude, alias_keys=None) -> DataFrame
# колонки: settlement, street_type, street, house, suffix, name_key, alias_key,
#          latitude, longitude
```

`alias_key` — ключ, по которому ищется известная пара «вывеска → лицензиат»
(§10, §12). По умолчанию он равен `name_key`; на стороне реестра его лучше
заполнить ИНН: название могут носить две неродственные компании, ИНН — нет.

Это единственный интерфейс между источником и правилом. Следствия:

- правило тестируется без данных проекта (130 модульных тестов, `pixi run licmatch-test`);
- смена источника — это новый адаптер, а не правка правила;
- симметрия сторон по адресу и расстоянию гарантирована по построению:
  `score_matrix(a, b)` не различает «объект» и «лицензию», кроме порядка осей
  матрицы. Единственная асимметрия — в члене названия: «общей вывеской» (§10)
  может быть только сторона `a`, и ключ алиаса стороны `a` сворачивается
  `brand_key()` (§12), а стороны `b` — нет.

## 4. Разбор адреса в топонимы

Адрес превращается в неизменяемую структуру `Toponym`:

| поле | смысл | пример |
| --- | --- | --- |
| `settlement` | населённый пункт внутри округа; `""` — сам город | `лесн речк` |
| `street_type` | канонический ключ типа улицы; `""` — тип не написан | `наб` |
| `street` | название улицы, слова со снятым окончанием, порядок сохранён | `северн двин` |
| `house` | номер дома, только цифры | `55` |
| `suffix` | литера дома + корпус/строение | `4` |

Две точки входа — по форме, в которой источник отдаёт адрес:
`parse_address_line()` для строки с запятыми и `parse_address_fields()` для
отдельных полей. Обе дают один и тот же `Toponym`.

Правила разбора и их обоснование:

- **Тип улицы** (`ул`, `пр`, `наб`, `ш`, …) распознаётся в любой позиции —
  `Троицкий пр-кт` и `проспект Ломоносова` — и в любом написании, полном или
  сокращённом, после чего сворачивается в один ключ.
- **`линия` намеренно не считается типом улицы.** Один источник пишет
  `3-я линия ул` (тип — `ул`, «линия» принадлежит названию), другой — `3-я линия`
  вовсе без типа. Признание «линии» типом сняло бы её с одной стороны и
  превратило точное совпадение в конфликт типов.
- **Инициалы отбрасываются**: `Тимме Я. Улица` → `тимме`, потому что вторая
  сторона пишет просто `улица Тимме`.
- **Лёгкий стемминг вместо морфологического анализатора.** У слова снимается
  одно флективное окончание, и никогда — ниже четырёх символов. Этого хватает,
  чтобы `Северной Двины` встретилось с `Северная Двина`, а `Воскресенская` — с
  `Воскресенской`, и мало, чтобы склеить разные названия. Ограничение в четыре
  символа — защита от схлопывания коротких фамилий.
- **Дом и корпус разбираются вместе**: `356 к4`, `45/3`, `13 с1`, `4 к1с3` и
  отдельный слот корпуса в реестре сводятся к паре (номер, корпус). Ключевое
  слово корпуса должно быть отдельным токеном: без этого «к» в `49 киоск`
  читается как корпус.
- **Город не является топонимом.** Он есть на обеих сторонах всегда, в любом
  написании (`г Архангельск`, `Архангельск город`, `городской округ Архангельск`),
  поэтому отбрасывается, а не оценивается. Населённый пункт **внутри**
  муниципалитета — настоящий топоним и сохраняется.

Согласие двух топонимов:

```
address = 0.6 * street + 0.4 * house
```

- `street` = `0.6 * token_sort_ratio + 0.4 * token_set_ratio` по стеммированным
  названиям. Смесь, а не одна метрика: `token_set` в одиночку даёт подстроке
  оценку 1.00 (`Победы` внутри `40-летия Великой Победы`), `token_sort` в
  одиночку штрафует за порядок слов, в котором источники расходятся законно.
- конфликт **написанных** типов улиц умножает `street` на 0.6 (если тип написан
  только с одной стороны — штрафа нет: молчание не есть противоречие);
- `house`: тот же номер и тот же корпус → 1.0; номер тот же, корпус написан
  только с одной стороны → 0.85; номер тот же, корпуса разные → 0.6; номера
  разные → **0.0**; дом не написан с обеих сторон → 0.5, с одной → 0.3;
- конфликт двух названных населённых пунктов умножает весь адресный член на 0.4;
  односторонняя запись — на 0.8.

## 5. Нормализация названий

Имя приводится к «различающей части»: снимаются кавычки, ё, организационно-
правовые формы (`ООО`, `АО`, `Общество с ограниченной ответственностью`…) и
торговые описатели, которые справочник дописывает к вывеске (`супермаркет`,
`магазин`, `павильон`…). Российские уставные наименования дублируются
(`… «ЛОЙ» Сокращенно: ООО "ЛОЙ"`) — берётся сокращённая часть.

Разрыв «лицензиат ↔ вывеска» закрывается **явной таблицей** из девяти
однозначных, публично известных пар (`тандер → магнит`, `агроторг → пятерочка`,
`альбион 2002 → бристоль`, …). Таблица намеренно короткая: в неё попадает только
то, что не требует доказательства. Всё остальное просто получает низкую оценку
по имени — и это допустимо, потому что вес имени наименьший из трёх.

Начиная с версии 1.1 к явной таблице добавлены два механизма, оба
необязательные: пары «вывеска → лицензиат», **выученные из данных** (§12) и
переданные в `score_matrix(aliases=...)`, и **список общих вывесок**
(`GENERIC_FASCIAS`, `is_generic()`), у которых член названия не оценивается
вовсе (§10). Для счёта вывесок по адресам есть второй ключ, `brand_key()`: он
выносит амперсанд, так что `Красное&Белое` и `Красное & Белое` (у `name_key()`
это два разных ключа) становятся одной вывеской `красное белое`. Оценка пары
этот ключ не читает; по нему ищется только алиас стороны `a`.

**Имя — тай-брейкер между лицензиями по одному адресу, а не довод в пользу того,
что адрес верен.**

## 6. Функция оценки пары

```
score = 0.50 * address + 0.20 * name + 0.30 * distance
distance = 1 - d / 100 м,   кандидаты обрезаются по d ≤ 100 м
```

Веса (`W_ADDR`, `W_NAME`, `W_DIST`) отражают доказательную силу, а не удобство:

- **адрес — половина веса**: лицензия выдаётся на *адрес места осуществления
  деятельности*, это единственное поле, где оба источника описывают один и тот
  же юридический объект;
- **расстояние — 0.30**: подтверждает, но не различает (см. §2, округление DMS);
- **имя — 0.20**: описывает разные сущности на двух сторонах (лицензиат против
  вывески), поэтому не может нести больше.

Член `name` бывает трёх видов, и вид сохраняется в матрице `Scores.name_kind`
(и в `Selection.name_kind` у выбранной пары): `fuzzy` — две строки сравнены
`WRatio`; `alias` — пара известна (явная таблица или §12), `name = 1.0`
независимо от строк; `generic` — вывеска общая, член не оценивается (§10).

Формула существует в двух видах: `pair_score()` — читаемое определение для одной
пары, `score_matrix()` — та же арифметика сразу по всем парам. Это оптимизация,
и расхождение оптимизации с определением — ровно тот класс дефектов, ради
которого написан `tests/test_scoring.py`: два вида сверяются на **каждой** паре
фикстуры, а не на выбранной вручную.

Матрица плотная (город — несколько миллионов пар). Блокирование (blocking) дало
бы скорость ценой единственного свойства, делающего результат аудируемым: что ни
один кандидат не был молча изъят у функции оценки (требование 3 из §1).

## 7. Два порога, а не один

```
score ≥ 0.45  (accept)      И      address ≥ 0.72  (addr_min)
```

Второй порог — не косметика, он делает основную работу.

Внутри 100 м **соседнее здание** тоже кандидат: та же улица, другой номер дома,
адресный член 0.60. На дистанции 30 м с любым сходством названий такая пара
преодолевает любой порог по сумме, достаточно низкий, чтобы сохранить настоящие
совпадения с плохими координатами. Расстояние здесь не арбитр (§2), а номер дома
— арбитр.

Величина 0.72 — это в точности оценка ситуации «та же улица, номер дома написан
только с одной стороны» (`0.6 * 1.0 + 0.4 * 0.3`). Явное расхождение номеров даёт
0.60 и отвергается. Ровно эта граница зафиксирована в тестах
(`test_toponym.py::TestAddressFloorSeparatesNeighbours`).

`addr_min = 0` восстанавливает неограждённую взвешенную сумму — режим для
сравнения, а не для публикации. В прикладном запуске это флаг `--addr-min 0`.

Каждое принятое совпадение помечается уровнем: `house` — обе стороны называют
одно здание, `street` — номер дома написан только с одной стороны (слабее; в
основном прогоне это 124 совпадения из 1 366).

## 8. Два маршрута допуска

**Геомаршрут** (`geo`): обе стороны имеют координату и находятся в пределах
`max_m`.

**Адресный маршрут** (`address`): у записи реестра пригодной координаты нет —
это 47 % строк. Здесь член расстояния **отбрасывается, а не оценивается нулём**,
оставшиеся два веса перенормируются:

```
score = (0.50 * address + 0.20 * name) / 0.70
```

и оба оставшихся члена обязаны преодолеть намеренно более высокий барьер:
`street ≥ 0.90` и `house ≥ 0.85`.

Почему не ноль: занулённый член расстояния снизил бы потолок такой пары до 0.70,
и идеальное адресное совпадение без координат никогда не попало бы в «сильный»
разряд — отсутствие данных превратилось бы в свидетельство против. Почему барьер
выше: доводов осталось два вместо трёх, и компенсировать это тихой
перенормировкой весов было бы подлогом.

Пары, не допущенные ни одним маршрутом, получают `score = NaN` — не ноль: «не
рассматривалось» и «рассмотрено и отвергнуто» различимы в выводе.

Разрыв в координатах сосредоточен в архиве: у 98 % **действующих розничных**
лицензий координата есть.

## 9. Выбор записи и подсчёт совпадений

Два решения разведены намеренно:

- **Допуск** — какие пары преодолели оба порога. Все допущенные записи реестра
  идут в подсчёт: «сколько лицензий по этому адресу» — другой вопрос, чем «какую
  из них процитировать».
- **Выбор** — какая единственная запись копируется в выходные колонки.
  Предпочитаемая запись (на практике — действующая лицензия) побеждает любую
  непредпочитаемую **независимо от оценок**. Поэтому статус объекта не может
  оказаться «архивная», пока по тому же адресу есть действующая.

Подсчёт ведётся **по различным ключам**, а не по строкам матрицы: реестр
записывает одну лицензию заново при каждом изменении статуса, и 20 строк по
одному адресу могут быть 9 лицензиями.

Обратное направление (`claimed_keys()`) — «какие записи реестра выгрузка вообще
объяснила» — считается отдельно и не является дополнением прямого: одну лицензию
могут claim'ить много объектов, а другую — ни один.

Предпочтений может быть несколько: `prefer` принимает кортеж масок в порядке
убывания приоритета (например, «действующая» выше «розничная»). Маска уровня
`k` снизу поднимает оценку на `PREFER_LIFT · 2^k`, так что каждый уровень
перебивает любую комбинацию нижележащих, а внутри одной комбинации уровней
решает оценка. Маска задаётся по строкам реестра `(n_b,)` или по парам
`(n_a, n_b)` — второе нужно, когда предпочтение зависит от объекта (табачной
строке — розничная лицензия, алкогольной — любая).

Два дополнительных ограничения выбора — **допустимость** и **исключительность**
— описаны в §11. Оба по умолчанию выключены, и без них выбор ведёт себя ровно
как в версии 1.0.

## 10. Нейтральный балл за название для общих вывесок

Вывеска `Продукты` не называет магазин — она называет **род** магазина. Под ней
в городе торгует сотня владельцев, и сравнение `продукты` с именем лицензиата
всегда даёт низкий `name`. В формуле §6 это означало штраф: пара «Продукты — ООО
Ромашка» по тому же адресу и в тех же метрах получала на 0.20 × (1 − name)
меньше, чем пара с именной вывеской, — за то, чего вывеска никогда не
утверждала. Это та же ошибка, от которой адресный маршрут (§8) защищает
отсутствующую координату: **отсутствие сведений оценивалось как свидетельство
против**.

Поэтому для общей вывески (`MatchParams.neutral_generic = True`, по умолчанию)
член названия **отбрасывается, а не оценивается нулём**, и его вес раздаётся
остальным с сохранением суммы весов:

```
геомаршрут:       score = (0.50 * address + 0.30 * distance) * 1.00 / 0.80
адресный маршрут: score = address
```

Что считается общей вывеской — закрытый список `GENERIC_FASCIAS` в ключах
`name_key()`: `продукты`, `продукты 24`, `алкоголь`, `разливное пиво`, `табак`,
`у дома` и подобные. Отдельная запись для `Кафе`, `Бар`, `Магазин` не нужна:
торговые описатели снимаются нормализацией (§5), такая вывеска сводится к `""`,
а пустой ключ — общий по определению.

Свойства, зафиксированные тестами (`test_scoring.py`):

- пара **без** общей вывески считается ровно по формуле §6, побитово так же,
  как в версии 1.0, при любом значении переключателя;
- `neutral_generic = False` восстанавливает старую арифметику и для общих
  вывесок (пустое имя снова даёт `name = 0`);
- известная пара (`alias`) сильнее общности: если выученная или явная таблица
  связывает общую вывеску с конкретным лицензиатом, член названия равен 1.0 и
  оценивается;
- `pair_score()` и `score_matrix()` совпадают на каждой паре фикстуры, в которой
  есть общие вывески на обоих маршрутах и алиасы.

Чего это **не** делает. Нейтральный балл не поднимает общую вывеску выше именной
по тому же адресу — он лишь перестаёт её штрафовать. Пара по-прежнему обязана
пройти оба порога §7, а `addr_min` на член названия не смотрит вовсе. Общая
вывеска проверяется только на стороне `a` (объекты): лицензиат вывески не имеет.

## 11. Распределение «одна точка — один объект»

Правило §9 выбирает запись **для каждого объекта независимо**. Пять объектов в
одном здании с одной лицензией получат её все пятеро — это честный ответ на
вопрос «есть ли по адресу лицензия» (§15, первый запрет), но неверный ответ на
вопрос «чья это лицензия». Для второго вопроса `select()` умеет исключительность.

**Единица** (`units=`) — метка точки реестра: лицензия по одному адресу, сколько
бы строк реестр под неё ни завёл. Строки с одной меткой — одна единица.
Правило: **одна единица — не более одному объекту, один объект — не более одной
единицы**. Назначение жадное (`greedy_assign`): все допущенные пары
сортируются по ранжированной оценке (с подъёмами `prefer`, §9), сильнейшая пара
забирает свою единицу, следующая — то, что осталось; объект, чью лучшую единицу
забрали, спускается к следующей свободной. Ничьи решаются меньшим индексом
объекта, затем меньшим индексом строки — детерминированно, повторный прогон
воспроизводит файл.

**Почему жадное, а не оптимальное.** Оптимальное назначение (венгерский
алгоритм) максимизирует **сумму** оценок и ради неё может отдать единицу более
слабой паре, если это позволит двум другим парам набрать больше. Такой исход
нельзя проверить глазами: чтобы понять, почему объекту досталась не его лучшая
лицензия, нужно пересчитать всю задачу. Жадное правило проверяется построчно —
«эту лицензию взял объект с более сильной парой, вот он, вот его оценка». Это
требование прозрачности из §1, и оно здесь важнее, чем суммарный балл.

**Раздел** (`partition=`) — группы объектов, внутри которых действует
исключительность. Алкогольный и табачный слои выгрузки законно претендуют на
одну и ту же точку (§15, четвёртый запрет): с разделом по слою каждый из них
получает её независимо.

**Сущность** (`entities=`) — метки записей выгрузки, описывающих **один и тот же
магазин** (две записи из двух файлов, два написания одной вывески). Единицу
захватывает сущность, а не запись: все записи сущности могут держать единицу,
которую держит любая из них. Без меток дубликат конкурирует сам с собой, и одна
его копия получает `taken`, указывая `rival` на собственного двойника, — ложный
конфликт. Разные сущности конкурируют как прежде: одну единицу внутри раздела
держит ровно одна сущность, а `rival` проигравшей записи всегда указывает на
запись **другой** сущности, которая эту единицу держит
(`test_exclusive.py::TestEntities`). Какие записи считать одной сущностью,
решает адаптер (например, одинаковый адрес и совпадающая вывеска); пакет метку
только исполняет.

Исход для объекта, оставшегося без единицы, — **не** «не найдено»:

| поле | смысл |
| --- | --- |
| `hit = False`, `taken = True` | допущенные и допустимые пары были, но все их единицы забрали более сильные пары |
| `rival` | индекс объекта, забравшего **лучшую** единицу этого объекта (иначе −1) |

**Допустимость** (`eligible=`) — маска пар (или строк реестра), которые
**можно выбрать**. Допущенная, но недопустимая пара остаётся в подсчётах (§9):
лицензия по адресу стоит, просто её нельзя цитировать для этого объекта —
например, табачной строке нельзя приписать лицензию общепита. Недопустимая пара
не занимает единицу. Объект, у которого допущенные пары есть, а допустимых нет,
получает `blocked = True` — это третье состояние, отличное и от «не найдено», и
от `taken`.

Без `units` и `eligible` выбор совпадает с версией 1.0: тест
`test_exclusive.py::TestOneOutletThreeObjects` фиксирует обе ветви на одном
здании с тремя объектами и одной лицензией.

## 12. Обучение пар «вывеска → лицензиат»

Явная таблица §5 покрывает федеральные сети. Местная сеть из пяти магазинов
торгует под одной вывеской от имени ООО, которое на неё не похоже, и никакой
список этого не знает. `learn_brands()` находит такие пары в самих данных.

**Голосование по адресам.** Каждый объект оценивается против каждой записи
реестра **без члена названия** — иначе ответ вошёл бы в вопрос. Настоящий
лицензиат вывески стоит почти на каждом её адресе; соседи по адресу от адреса к
адресу разные. Просуммированный по адресам вывески, настоящий лицензиат
накапливает голоса, соседи — нет. Голоса считаются по **различным адресам**
(`sites=`), так что две записи одного магазина голосуют один раз. Общие
вывески (§10) не голосуют и в таблицу не попадают.

**Поправка на базовую частоту (lift).** Федеральная сеть стоит рядом с заметной
долей всех магазинов города и собирает голоса любой вывески. Поэтому пара
засчитывается, только если лицензиат встречается на адресах вывески в
`min_lift` раз чаще, чем на адресах вообще:

```
cover     = доля адресов вывески, где лицензиат допущен
base_rate = доля всех адресов, где лицензиат допущен
lift      = cover / base_rate
```

Лицензиат, стоящий почти везде, имеет `base_rate ≈ 1` и `lift ≈ 1` при любой
вывеске — он не проходит, сколько бы голосов ни собрал.

**Конкуренция за точку.** Табачный киоск, который всегда стоит внутри
супермаркета, соберёт лицензию супермаркета на каждом своём адресе, и lift у
него будет тот же. Поэтому голос — это не «лицензиат присутствует», а
«**точка досталась**»: единицы реестра раздаются по правилу §11, по одной на
объект, и голос — это единица, которую объект действительно получил. Текущие
голоса вывески возвращаются в следующий раунд как приор к оценке пары:

```
prior = log((c + s·b) / (n + s)) − log(b)       value = strength + 0.15 · prior
```

где `n` — адреса вывески, `c` — те из них, где пару выбрал этот лицензиат,
`b = 0.05`, `s = 1`. Приор **никогда не учитывает собственный адрес объекта**
(leave-one-site-out): пара не может голосовать сама за себя, а вывеска с
единственным адресом получает приор ровно 0. Супермаркет, чей голос за
лицензиата подкреплён и его собственными адресами, где киоска нет, получает
приор выше и забирает общую точку; киоск, чей голос держался только на этих
общих точках, остаётся без голосов, и его приор к этому лицензиату в следующем
раунде становится отрицательным.

Первый раунд засеян **присутствием** (каждый допущенный лицензиат на каждом
адресе), а не пустым приором. Без затравки первый раунд решается сырой оценкой
и порядком объектов: при равных оценках киоск, записанный раньше супермаркета,
забирал общую точку, получал полный голос, и следующий раунд его подтверждал —
устойчивая неверная неподвижная точка. Тест
`test_brands.py::TestCompetitionForTheOutlet` проверяет оба порядка.

**Остановка.** Раунды идут, пока назначение меняется (не больше `max_iter`).
Возможен **двухтактный цикл**: две вывески делят одну точку на двух адресах, и
победитель на одном адресе отдаёт приор проигравшему на другом, так что они
меняются местами каждый раунд. Цикл распознаётся (назначение равно
позапрошлому), и тогда объекты, чей выбор в двух состояниях различается, **не
голосуют ни за кого**; остальные сохраняют свои устойчивые голоса. В результате
это видно: `cycle = 0` — сошлось, `2` — остановлено на цикле, `−1` — исчерпан
`max_iter`; `oscillating` — число колеблющихся объектов. На данных исследования
таких объектов 3 из 945.

**Пороги** (`BrandParams`, пара принимается при выполнении всех):

| параметр | значение | смысл |
| --- | --- | --- |
| `min_sites` | 3 | различных адресов, где точка досталась вывеске; меньше — совпадение |
| `min_share` | 0.3 | доля адресов вывески; не большинство, чтобы франшиза двух операторов дала обоих |
| `min_lift` | 3.0 | во сколько раз чаще, чем в среднем по городу |
| `franchise_top_max` | 0.5 | вывеска, чей лучший лицензиат взял меньше половины адресов, — франшиза |
| `franchise_min_share` | 0.1 | для операторов франшизы — вместо `min_share` |
| `franchise_holder_cover` | 0.5 | …но только если не меньше половины точек лицензиата стоят на адресах вывески |

**Франшиза и проверка со стороны лицензиата.** Пара проходит по доле, если
`share ≥ min_share`, **или** если одновременно: вывеска — франшиза (`franchise`
в таблице: её лучший лицензиат взял меньше `franchise_top_max` адресов),
`share ≥ franchise_min_share` **и** `holder_cover ≥ franchise_holder_cover`.
`min_sites` и `min_lift` действуют всегда.

Надо сказать прямо: правило франшизы введено под один случай — `Петровский` в
Архангельске, 25 адресов, не меньше пяти операторов, крупнейший держит 28 %;
строгая доля 0.3 отсекла бы всех, кроме одного. Само по себе пониженное
требование к доле (0.1) обобщается плохо: на любой вывеске без доминирующего
лицензиата оно впускает **соседа по зданию**, который просто стоит рядом с
тремя её магазинами. То, что делает правило переносимым, — вторая проверка, с
**другой стороны** пары:

```
holder_cover = доля точек лицензиата (единиц, до которых дошёл хоть один объект),
               к которым дошли объекты этой вывески
```

Оператор франшизы — это в основном и есть франшиза: большая часть его точек
стоит на её адресах. Компания, у которой из двадцати точек две оказались в
зданиях вывески, — сосед (так в данных исследования пара `Кедр`/`Фасоль`:
2 из 20, отвергнута), а операторы `Петровского` проверку проходят. Проверка
действует только на франшизной ветви: пара, прошедшая `min_share`, о своём
`holder_cover` не спрашивается. Вывеска, где один лицензиат доминирует
(Магнит, 0.86), франшизой не является и сохраняет строгий порог 0.3 для
любого второго лицензиата — это не пускает соседа в колонку федеральной сети.

**Выход** — таблица, одна строка на пару (вывеска, лицензиат) с хотя бы одним
назначенным адресом: `sites_present`, `sites_assigned`, `share`, `cover`,
`base_rate`, `lift`, `holder_cover`, `franchise`, `accepted`, `loo_accepted`,
`holders_for_fascia`, — множество принятых пар `pairs` для
`score_matrix(aliases=...)` и словарь `site_votes`: пара → множество адресов,
чьё назначение за неё проголосовало. Ключ вывески в
нём — `brand_key()`; `score_matrix()` сворачивает ключ алиаса стороны `a` тем же
`brand_key()`, так что выученная `красное белое` находит объект
`Красное&Белое`.

**Leave-one-site-out — дважды.** Принцип «пара не свидетельствует сама за
себя» применяется в двух местах.

1. **В приоре** (выше): приор объекта никогда не учитывает его собственный
   адрес.
2. **В члене названия.** Выученная пара, переданная в `aliases=`, поднимает
   `name` до 1.0 — в том числе на тех самых адресах, голоса которых её
   породили. Если пара держится ровно на них, она подтверждает сама себя:
   адрес голосует за пару, пара повышает оценку адреса. Поэтому таблица несёт
   `loo_accepted` — приняли бы пару, если убрать **любой один** из
   голосовавших адресов (порог пересчитывается с `sites_assigned − 1`,
   `fascia_sites − 1`, `sites_present − 1`). Пара ровно на `min_sites` адресах
   принята, но `loo_accepted = False`; на `min_sites + 1` — и то и другое.
   Где пара не `loo_accepted`, адаптер на её адресах из `site_votes` должен
   вернуть член названия к обычному сравнению строк; на остальных адресах
   вывески — там, где пара ничего не голосовала, — алиас действует. Это
   решение адаптера, пакет даёт для него оба поля.

**Архивные лицензии никого не исключают.** Пара, опирающаяся только на
архивные записи реестра, говорит о том, кто **торговал** под вывеской, а не кто
торгует сейчас. Использовать её, чтобы **отнять** у объекта действующую
лицензию другого лицензиата (признать архивную запись «своей» и отказать
действующей), нельзя: устаревшее свидетельство не может перевешивать текущее.
Отбор записей по статусу — дело адаптера (через `eligible=` и `prefer=`, §9,
§11); принцип такой: если по адресу стоит действующая лицензия того же вида
деятельности, архивная запись допустима к выбору только при совпадении
названия.

**Таблица — гипотезы, а не факты.** Выученная пара — это утверждение «под этой
вывеской на N адресах точка досталась этому лицензиату, в X раз чаще
случайного» со счётом за ним. Её нужно прочесть глазами, прежде чем передавать
в оценку, и любой результат, полученный с выученными алиасами, обязан сказать
об этом рядом с числами. Выученная пара поднимает член названия до 1.0 и
никогда не касается адресного порога: неверная пара может переставить выбор
между лицензиями **по одному адресу**, но не может привести лицензию соседнего
дома.

**Почему не кластеризация объектов.** Очевидная альтернатива — описать каждый
объект вектором по лицензиатам (какие лицензиаты стоят по его адресу) и
кластеризовать объекты: сеть должна собраться в кластер вокруг своего
лицензиата. Это не работает, и причина в самих векторах:

- вектор объекта описывает **соседей по адресу**, а не объект: в нём столько же
  случайных лицензиатов из того же здания, сколько настоящих;
- он почти пуст — медиана **2 ненулевые координаты из ~480**; расстояние между
  такими векторами определяется тем, совпал ли единственный сосед;
- в итоге сеть **рассыпается на десятки кластеров**: каждый её магазин ближе к
  своим соседям по зданию, чем к другим магазинам сети.

Сигнал «один лицензиат на всех адресах» существует только в **сумме по
адресам** одной вывески. Поэтому единица агрегации — вывеска, а не объект: сначала
объекты сворачиваются по вывеске, затем проверяется, какой лицензиат повторяется
от адреса к адресу чаще, чем по городу в среднем. Это и есть голосование выше.

## 13. Калибровка порогов

Порогов три, и каждый получен своим способом.

**`max_m = 100 м`** — не оптимизирован, а выбран из свойств источника: ошибка
координат реестра (≈ 31 м на секунду округления, плюс привязка к центру
здания) делает меньший радиус произвольно жёстким, а больший — бессмысленным,
поскольку различать соседей всё равно приходится по номеру дома.

**`accept = 0.45`** — получен лестницей порогов (`--calibrate`) и просмотром
десяти случайных совпадений в каждой полосе оценок. Лестница на основном
прогоне:

| порог | принято без адресного барьера | принято с `addr ≥ 0.72` |
| --- | --- | --- |
| ≥ 0.35 | 1 484 (87.6 %) | 1 370 (80.9 %) |
| ≥ 0.45 | 1 446 (85.4 %) | **1 366 (80.6 %)** |
| ≥ 0.55 | 1 367 (80.7 %) | 1 330 (78.5 %) |
| ≥ 0.75 | 1 025 (60.5 %) | 1 024 (60.4 %) |

Содержательный смысл границы: ниже 0.45 лучшее совпадение объекта — это
лицензия дальше ~80 м, чьё название не говорит ничего. Это не свидетельство.

Разрыв между колонками — это и есть соседние здания из §7: на низких порогах
адресный барьер снимает 80–114 совпадений, к 0.55 разрыв падает до 37, а к 0.75
исчезает совсем (1 025 против 1 024), потому что пара с несовпадающим номером
дома высокой суммы почти никогда не набирает. Иначе говоря, порог по сумме и
адресный барьер отсекают **разные** пары, и заменить второй первым нельзя:
подняв `accept` до 0.75, мы вместе с соседями потеряли бы треть настоящих
совпадений.

Чувствительность результата к `accept` мала (1 370 → 1 330 в диапазоне
0.35–0.55), к `addr_min` — велика. Порог, который следует обсуждать при
пересмотре методики, — второй.

**`addr_min = 0.72`** — не подобран по данным, а выведен из шкалы адресного
члена (§7). Это делает его устойчивым: он не перестанет работать на другом
городе или другом реестре.

`strong = 0.75` ничего не отсекает — это разряд «совпадение, которое не нужно
защищать», для раздельной отчётности.

## 14. Проверка правила

Независимого пообъектного эталона для этой связки не существует, поэтому
проверка ведётся тремя способами, и ни один из них не является измерением
точности в строгом смысле.

1. **Модульные тесты** (130, `pixi run licmatch-test`) фиксируют правило на тех
   парах, ради которых оно написано: четыре кросс-источниковые пары из §2
   преодолевают адресный порог; соседний дом получает ровно 0.60 и
   отвергается; матричная форма совпадает с формулой на каждой паре фикстуры,
   включая общие вывески и алиасы на обоих маршрутах; пары без общей вывески
   считаются ровно как в версии 1.0; предпочтение действующей лицензии
   перебивает более высокую оценку; подсчёт ведётся по различным ключам;
   исключительность отдаёт точку сильнейшей паре и называет `rival`;
   обучение пар (§12) на синтетических городах находит лицензиата вывески, не
   берёт соседей, федеральную сеть и общие вывески, решает конкуренцию киоска и
   супермаркета при любом порядке объектов, принимает операторов франшизы и
   отвергает лицензиата, чьи точки в основном стоят вне её (`holder_cover`),
   различает `accepted` и `loo_accepted` на границе `min_sites` и распознаёт
   двухтактный цикл; сущности (`entities=`) держат одну точку, не конкурируя
   сами с собой.
2. **Обратное покрытие** — сильнейший из доступных аргументов, потому что оно
   проверяет правило в направлении, где эталон есть: **97.7 % из 442
   действующих розничных лицензий «навынос»** и 88.1 % из 135 действующих
   лицензий общепита имеют объект выгрузки по своему адресу. Если бы правило
   систематически промахивалось по адресам, эта доля не могла бы быть такой.
3. **Ручной просмотр по полосам оценок** (`--calibrate`) — по десять случайных
   совпадений в каждой полосе, включая полосу ниже порога принятия, что и
   позволяет увидеть, что именно порог отсекает.

Прямая доля совпадений — 1 366 из 1 694 записей (80.6 %) — **не является
метрикой качества правила**: несовпадение может означать и ошибку правила, и
отсутствие лицензии, и ошибку адреса в выгрузке. Разделить эти причины
имеющимися данными нельзя.

## 15. Что результат не означает

Четыре запрета, каждый из которых уже приводил к неверному прочтению.

- **Лицензия — не магазин.** Действующая запись означает, что по адресу
  кто-то держит лицензию, а не что данный объект и есть лицензиат. Там, где в
  одном здании несколько лицензий (торговый центр, первый этаж на пять
  помещений), все объекты здания получают один и тот же набор. Режим
  исключительности (§11) отдаёт каждую лицензию одному объекту, но и тогда
  это «сильнейшая пара по адресу», а не доказательство, что лицензиат — именно
  этот магазин.
- **«Нет в реестре» — не «не торгует алкоголем».** Это объединение трёх
  ситуаций: лицензии действительно нет; лицензия оформлена на адрес, до
  которого не дошёл ни один маршрут; адрес в выгрузке ошибочен.
- **Реестр — не список работающих точек.** Он исторический: в городской
  выборке действующих лицензий 585 из 2 100. Любой подсчёт обязан фильтровать
  по статусу.
- **Совпадение отвечает только за тот продукт, который реестр лицензирует.**
  В настоящем исследовании это алкоголь; табачного реестра не существует, и
  табачные строки сопоставляются с **алкогольными** лицензиями. Такое
  совпадение помечается `probable` и означает косвенный довод (алкоголь и табак
  продаются через один прилавок), а не подтверждение. `probable` — **метка, а не
  вероятность**: измерить силу этой связи нечем. Складывать `direct` и
  `probable` в один заголовочный показатель нельзя. Подробнее —
  `docs/v4_egais_match.md`.

## 16. Воспроизводимость

- Правило **детерминировано**: никакой случайности, никакого внешнего сервиса.
  Единственное «обучение» — необязательное `learn_brands()` (§12) — это
  детерминированная итерация без случайной инициализации: ничьи в назначении
  решаются индексами, так что и оно воспроизводится побайтово. Выученные пары
  входят в оценку только если адаптер явно передал их в `aliases=`. Повторный прогон на тех же входах даёт побайтово тот же
  файл (проверено при выделении пакета: три выходных файла совпали с эталоном
  до байта).
- Все настраиваемые числа собраны в неизменяемых объектах `MatchParams` и
  `BrandParams`;
  прикладной запуск печатает их в шапку сводки. Любой результат, полученный не
  на значениях по умолчанию, обязан называть свои настройки рядом с числами.
- Зависимости: `numpy`, `pandas`, `rapidfuzz`. Версия правила —
  `licmatch.__version__`; при изменении любого порога или веса её следует
  поднимать, потому что от неё зависят опубликованные числа.

## 17. Применение к другому источнику

Нужен только адаптер — примерно тридцать строк:

```python
import licmatch as lm

CITY = lm.home_city_re("Архангельск")

a = lm.side([lm.parse_address_line(v, CITY) for v in export["address"]],
            [lm.fascia_name(v) for v in export["name"]],
            export["lat"], export["lon"])
b = lm.side([lm.parse_address_fields(s, h, CITY, sub, blk)
             for s, h, sub, blk in registry[["street", "house", "settlement", "block"]].values],
            [lm.holder_name(v) for v in registry["holder"]],
            registry["lat"], registry["lon"])

sel = lm.select(lm.score_matrix(a, b, lm.DEFAULTS), lm.DEFAULTS,
                prefer=registry["in_force"].to_numpy(bool),
                keys=registry["licence_no"],
                groups={"matched": None, "active": registry["in_force"].to_numpy(bool)})
```

Что при этом обязательно пересмотреть:

- **таблицу торговых алиасов** — она про конкретный рынок (`RU_RETAIL_ALIASES`);
  местные сети лучше выучить (`learn_brands()`, §12), прочитать таблицу и
  передать принятые пары в `score_matrix(aliases=...)`, указав на стороне
  реестра `alias_keys` = ИНН;
- **список общих вывесок** (`GENERIC_FASCIAS`) — он тоже про рынок и язык;
- **`home_city_re()`** — город исследования отбрасывается только если назван;
- **`max_m`** — зависит от точности координат нового реестра;
- **словарь типов улиц** — если новый источник пишет типы, которых нет в
  `TYPE_TABLE`, они останутся в названии улицы и снизят сходство.

Чего менять **не** следует без повторной калибровки и пересчёта всех
опубликованных чисел: весов и `addr_min`.

## 18. Известные ограничения

- **Номер дома сравнивается как число** в матричной форме и **как строка** в
  однопарной. Для адресов с ведущими нулями (`д. 05`) две формы разошлись бы;
  в имеющихся данных таких записей нет. Если источник их допускает, номер
  следует нормализовать в адаптере.
- **Стемминг — эвристика.** Одно окончание, минимум четыре символа: этого
  достаточно для падежей русских топонимов и недостаточно для сложных случаев
  (супплетивные формы, аббревиатуры). Ошибка здесь снижает `street` и
  проявляется как пропуск, а не как ложное совпадение, — направление,
  выбранное сознательно (требование 1 из §1).
- **Плотная матрица** ограничивает масштаб: несколько миллионов пар помещаются в
  память, сотни миллионов — нет. Для большего города потребуется блокирование, и
  тогда придётся отдельно доказывать, что оно ничего не отсекает.
- **Корпус/строение сводятся к одному полю** `suffix`: литера дома и номер
  корпуса не различаются. Это соответствует тому, как их пишут источники, но
  теряет информацию там, где различие существенно.
- **Жадное распределение не оптимально** (§11) — намеренно. Сумма оценок
  назначения может быть ниже достижимой; зато каждое решение объясняется одной
  более сильной парой.
- **Ничьи в жадном распределении решает порядок.** При равных ранжированных
  оценках точку получает объект с меньшим индексом, затем строка с меньшим
  индексом. Это детерминированно, но произвольно: переупорядочив выгрузку,
  можно получить другого владельца точки. Равные оценки у разных объектов
  реальны (одинаковый адрес, одна координата здания, общие вывески с
  отброшенным членом названия, §10); такой исход следует читать как «точку
  делят», а не как решение в пользу победителя. В обучении пар (§12) порядок
  больше не решает первый раунд — его снимает затравка присутствием, — но ничья
  внутри раунда по-прежнему решается индексом.
- **Сущности — эвристика адаптера.** Пакет доверяет меткам `entities=`
  безусловно. Слишком широкая метка (два разных магазина одного здания под
  одной вывеской) позволит обоим держать одну лицензию — вернётся ровно та
  проблема, которую решает исключительность; слишком узкая оставит ложный
  конфликт дубликата с самим собой.
- **Список общих вывесок закрыт.** Вывеска, которой в нём нет (`Продукты у
  Любы`), оценивается по имени как обычно, а редкая именная вывеска, попавшая в
  список по совпадению, лишится члена названия. Ошибка в обе стороны касается
  только тай-брейкера (§5) и не трогает адресный порог.
- **Выученные пары зависят от покрытия выгрузки.** Вывеска меньше чем с тремя
  адресами не учится никогда; франшиза, операторы которой разнесены по
  городу неравномерно, может дать не всех операторов. Двухтактный цикл
  (§12) лишает колеблющиеся объекты голоса — это консервативно, но означает,
  что пара двух вывесок, делящих одну точку, не будет выучена ни для одной.
- **Населённый пункт сравнивается по названию, а не по коду.** Омонимичные
  посёлки внутри одного округа будут неразличимы.
